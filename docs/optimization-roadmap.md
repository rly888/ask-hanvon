"时间"碎片）出现了非确定性回答了无关内容——新增 **主题锚词守卫**（`answer.topic_coherence_check`）：
问题锚词（去泛词）在回答与全部引用片段中均缺失 → 强制拒答。修复后拒答 100% 稳定。

**用户反馈修复（引用纪律）**：「《西游记》讲了什么」这类概览问题曾误拒——
模型把 [1] 标在「全书综述句」尾部，综述句非单片段原句，被交叉验证判为无据而剥除，
触发「无引用可验证=拒答」。修复：① prompt 明确「跨片段综述句须并列标注 [1][2][3]」；
② 答案级证据阈值策略化（`answer.answer_level_threshold` 0.25→0.12，综述句对片段内容词的
低覆盖容忍；幻觉仍由主题锚词守卫+句级通道兜底）。实测：概览类问题恢复回答，
《时间简史》类陷阱题拒答保持 100%。

**安全升级 ① ②（Prompt 注入纵深加固）**：
- ① 结构式隔离：资料区一律由系统包裹 `<context>` 标签；不可信内容中的
  类标签片段经 `sanitize_context_tags` 转义，**伪造标签的检索块直接剔除**
  （dropped_untrusted 计数）——资料区标签结构只能由系统生成，是程序化保证；
- ② 灰区/弱信号 LLM 二判：规则 0.3–0.7 灰区与「弱信号预筛」（授权书话术/系统消息

- 注入对抗集（32 条：9 强样本 + 11 变体 + 12 正常咨询）入评测，新增 security 门禁套件
  （strong≥0.95 / variant≥0.70 / 正常误伤≤0.05）。
- **实测**：strong_recall=1.0、variant_recall=0.91、benign_fp=0.0；规则补强两处
  （"你的 system prompt"空格盲区、"忘记…初始设定"跨距）由对抗集在开发期就暴露。
- 门禁全绿后 RAG 引用率 0.977 / 拒答 1.0 无回退（结构隔离对生成质量零副作用）。

## 1. P0 · 立即优化（1–2 周内，高收益低成本）

### P0-1 接入真实 Embedding API，向量召回语义化 ⭐收益最大

- **现状**：`nlp.LocalEmbedder`（jieba 词元 + 字符二元组特征哈希，256 维）——本质是字面相似，
  对「八大行星 vs 八颗行星」「赵子龙 vs 赵云」等同义改写无能为力；POC 时智谱 embedding-3
  因余额不可用而临时采用本地方案。
- **问题**：语义检索名不副实；跨表述问题（口语化提问）召回依赖 BM25 兜底。
- **方案**：
  1. 充值/开通 embedding 资源，配置 `EMBED_BASE_URL + EMBED_MODEL + EMBED_API_KEY`
     （代码已支持，`modelhub/gateway.embed` 自动切换，**无需改代码**）；
  2. 批量回填：`python -m scripts.ingest_books books --reindex`（重建 embedding 与 FTS）；
  3. 用黄金集做 A/B：策略中心调 `retrieval.weights`（建议从 bm25:0.5/vector:0.5 起步），
     以 `citation_accuracy` / `retrieval_recall` 为准绳择优；
  4. 嵌入结果版本号写入 `chunks.embedding_model` 字段，换模型强制重建（防新旧向量混算）。
- **涉及模块**：`modelhub/`、`pipeline/embed.py`、`rag/retriever.py`、`db.py`（加一列）。
- **工作量**：0.5–1 天（含回归评测）。
- **验收**：黄金集 retrieval_recall ≥ 98%，口语化改写题（新增 20 题语义组）召回 ≥ 90%。

### P0-2 事件消费多实例安全（现网风险）

- **现状**：`events/collector` 在应用进程内起消费线程；`event_fetch_batch` 用
  `WHERE status='new' ORDER BY id LIMIT ?` 取批，无行锁。
- **问题**：uvicorn 多 worker（`--workers 2`）或多实例部署时，**同一批事件会被重复消费**
  （特征重复累加、事件明细重复插入）。这是当前架构里最接近"数据错误"的隐患。
- **方案**（按部署形态择一）：
  1. 单实例约束：启动时 `kv_set("consumer_lock", instance_id+心跳)` 抢锁，仅持锁实例起线程
     （最快落地）；
  2. SQLite `UPDATE ... SET status='processing' WHERE id IN (...) AND status='new'` 按受影响行数
     认领 + 超时回收（robust）；
  3. 迁移 Kafka/Redis Stream 时换成消费组（P4 一并做）。
- **涉及模块**：`events/collector.py`、`db.py`。
- **工作量**：0.5 天。
- **验收**：双进程同时跑 `flush_once`，`events` 表与特征值无重复（写一个并发测试）。

### P0-3 检索融合升级：短语匹配 + RRF

- **现状**：BM25 是 OR 词元匹配（`nlp.fts_match_query`）；融合是 minmax 线性加权；
  引用准确率对词序/短语敏感的问题（如书名、事件名）靠标题词×2 加权补救。
- **问题**：OR 匹配会把「长坂桥」匹配到只含「桥」的块；线性加权对两路分数量纲敏感。
- **方案**：
  1. FTS 查询加短语通道：整句 jieba 分词后的连续二元组作短语约束
    （`"长坂" "坂坡"` NEAR 语义），或直接查原始子串（LIKE 兜底通道）；
  2. 融合换 **RRF（Reciprocal Rank Fusion）**：`score = Σ 1/(k+rank)`，k=60，
     消除量纲问题，与策略中心权重解耦（保留线性加权作为可选策略 `retrieval.fusion=rrf|linear`）；
  3. 黄金集回归 + 调参。
- **涉及模块**：`nlp.py`、`rag/retriever.py`、`ops/strategies.py`（默认值）。
- **工作量**：1 天。
- **验收**：retrieval_recall ≥ 98%，短语类问题（新增 10 题）Top3 命中率 ≥ 95%。

### P0-4 LLM 语义缓存（成本与延迟双降）

- **现状**：结果缓存 key = 归一化 query + Top6 chunk id（精确匹配）。
- **问题**：「孙悟空的师父是谁」与「悟空拜谁为师」互不命中，重复付费重复等待。
- **方案**：在精确缓存之下加一层**语义缓存**：query 向量与近期 query 向量余弦 ≥ 0.92
  且 Top1 chunk 集合重叠 ≥ 50% → 直接复用答案（TTL 单独配置，如 6h；答案带 `cached_semantic` 标记）。
  向量来自 `gateway.embed`（P0-1 后语义质量更好）。
- **涉及模块**：`generation/answer.py`（缓存层）、`ops/strategies.py`（开关与阈值）。
- **工作量**：1 天。
- **验收**：重复语义问题二次响应 < 200ms；mh_calls 成本日环比下降可观测；
  评测（use_cache=false 口径）指标不回退。

### P0-5 评测门禁接入 CI + Judge 模型治理

- **现状**：门禁靠手动 `python -m scripts.run_eval`；judge 复用 weak 模型。
- **问题**：变更容易漏跑回归；judge 与被测同源，有"自己判自己"偏差。
- **方案**：
  1. GitHub Actions / Jenkins：PR 触发 `run_eval --suite all`（离线模式跑，快且免费），
     门禁失败阻断合并；每晚全量（LLM 在线模式）；
  2. judge 换独立更强模型（`JUDGE_MODEL` 环境变量，如 glm-4-plus），与被测模型解耦；
  3. judge 结果抽样人工复核（每周 20 题），校准 judge 与人工一致率（目标 ≥ 85%）。
- **涉及模块**：`evals/rag_eval.py`（judge 路由）、CI 配置、`config.py`。
- **工作量**：1 天。
- **验收**：CI 红灯阻断 demo；judge-人工一致率 ≥ 85%。

### P0-6 认证强化：刷新令牌 + 吊销 + 口令策略

- **现状**：HS256 JWT（72h），无 refresh、无登出吊销；口令仅长度校验。
- **问题**：令牌泄露 72h 内无法作废；无"退出登录全端生效"。
- **方案**：
  1. access token 短期（2h）+ refresh token（7d，落 `kv`/新表，可吊销）；
  2. `POST /api/auth/logout` 吊销当前 refresh；登录时旧 refresh 全端失效（可选）；
  3. 口令策略：长度 ≥ 8 + 常见弱口令黑名单；连续失败 5 次锁定 15 分钟（防爆破）。
- **涉及模块**：`server/auth.py`、`server/routes_public.py`、新表 `auth_tokens`。
- **工作量**：1 天。
- **验收**：吊销后旧 refresh 不可用；锁定逻辑有测试覆盖。

## 2. P1 · RAG 质量深化（2–4 周）

### P1-1 Chunk 策略升级：父子检索（small-to-big）

- **现状**：固定 480 字符滑窗（overlap 96），检索与生成同粒度。
- **问题**：窗口切分会把完整论述拦腰截断；小块检索准但信息薄，大块信息全但稀释分数。
- **方案**：检索用**子块**（当前 480），命中后回填**父块**（整章或 ~1500 字）进上下文；
  chunk 表加 `parent_id`；`build_context` 做父块去重与预算控制。
- **涉及模块**：`pipeline/chunk.py`、`db.py`、`rag/context.py`。
- **工作量**：2 天。
- **验收**：长论述类问题（"讲讲赤壁之战的完整过程"）答案完整度（judge）提升 ≥ 10%。

### P1-2 查询理解升级：LLM 改写 + 多查询

- **现状**：指代消解为规则（`last_book` + 指代词表），无查询扩展。
- **问题**："它讲的是哪个朝代的事"这类省略/口语问法改写受限；一词不匹配即漏检。
- **方案**：
  1. LLM Query Rewrite（weak 模型，输出 JSON：`{rewritten, keywords[], book_title}`），
     规则结果优先、LLM 兜底（现结构已支持）；
  2. 多查询检索：原 query + 改写 query 各检一路，RRF 融合；
  3. （可选 P3）HyDE：让模型先生成假设答案再检索。
- **涉及模块**：`conversation/intent.py`、`rag/retriever.py`、`tools/book_qa.py`。
- **工作量**：2 天（含延迟预算：rewrite 用 weak 模型 + 800ms 超时降级原查询）。
- **验收**：多轮指代题（新增 15 题）成功率 ≥ 90%；P95 延迟增幅 ≤ 800ms。

### P1-3 引用验证升级：向量相似度 / NLI

- **现状**：`citation._claim_supported` 用词元覆盖 ∨ 二元组 ∨ 8gram（阈值 0.45/0.30/0.35，
  是为容忍转述调出来的经验值）。
- **问题**：词面启发式存在两向误差——过度拒绝（同义改写大）与漏放（bigram 碰撞，
  如"宝船木材"题模型借"宝船"共现答出无据细节，拒答率 13/14 的那 1 例漏网即此类）。
- **方案**：
  1. P0-1 就绪后，加**向量余弦通道**（claim embedding vs chunk embedding ≥ 0.55）；
  2. 进阶：轻量 NLI（ entailment 判断）或 LLM 二判（仅对"边界分数"0.3–0.5 的引用二判，
     控制成本）；
  3. 阈值搬进策略中心，灰度可调。
- **涉及模块**：`generation/citation.py`、`ops/strategies.py`。
- **工作量**：1–3 天。
- **验收**：黄金集 false_refusal ≤ 3% 且拒答漏网 = 0；新增"细粒度幻觉对抗集"（30 题）
  拦截率 ≥ 80%。

### P1-4 上下文构建优化：句子压缩 + 动态预算

- **现状**：整块进上下文（3600 字符预算，每书 cap 3 块），尾部截断。
- **问题**：块内无关句占预算，挤掉有用证据；预算固定不分场景。
- **方案**：
  1. 句子级筛选：块内句子按 query 词元/向量相关度过滤，保留 Top 句（保序）；
  2. 预算按场景配置（QA 3600 / 比较 2×1800 / 多轮 +20%）；
  3. 证据排序：与 query 最相关的块放头尾（lost-in-the-middle 缓解）。
- **涉及模块**：`rag/context.py`、`ops/strategies.py`。
- **工作量**：1–2 天。
- **验收**：同预算下 answer_pass_rate 不降、单次 prompt token 下降 ≥ 15%。

### P1-5 Prompt 版本管理 + 评测联动

- **现状**：prompt 是 `generation/prompts.py` 字符串常量。
- **问题**：改 prompt = 盲改，无法回答"哪个版本的 prompt 引用率更高"。
- **方案**：prompt 模板入库（`ops_prompts` 表：name/version/template），运行时按
  `answer.prompt_version` 策略取用；eval_runs 记录 prompt 版本；A/B 直接以 prompt 为变量。
- **涉及模块**：`generation/prompts.py`、`ops/strategies.py`、`evals/`。
- **工作量**：1–2 天。
- **验收**：两次 prompt 变更走"改版→回归→择优→切流"流程，历史可追溯。

## 3. P2 · Agent 与对话体验

### P2-1 多步规划与工具 DAG

- **现状**：Planner 单意图→单工具；「比较 A 和 B，再推荐类似的」会被拆散。
- **方案**：
  1. 短期：规则复合意图（compare→recommend 链式 plan，executor 顺序执行已有）；
  2. 中期：引入 LLM Planner 输出 JSON 步骤图（含依赖），executor 按依赖并行；
  3. 评估 LangGraph（计划 §4 备选）：仅当出现真正的循环/反思需求再引入，避免重框架。
- **涉及模块**：`agent/planner.py`、`agent/executor.py`。
- **工作量**：3–5 天。
- **验收**：新增复合任务用例集（10 例）完成率 ≥ 90%。

### P2-2 工具并行执行 + 分层超时

- **现状**：executor 顺序执行；统一 25s 工具超时。
- **方案**：无依赖步骤并发（线程池）；超时分层：检索类 5s / 生成类 30s；
  单工具失败不阻塞无依赖兄弟步骤。
- **涉及模块**：`agent/executor.py`、`tools/schema.py`（timeout 字段已有）。
- **工作量**：1 天。
- **验收**：双工具任务端到端延迟 ≈ max(单工具) 而非求和。

### P2-3 回答自检（低置信二次检索）

- **现状**：一次检索一次生成；拒答即终结。
- **方案**：拒答或 `verified_ratio < 0.5` 时自动触发一次**改写重检索**（P1-2 的 rewrite），
  二次仍失败才拒答并附「猜你想问」推荐；控制最多 1 次重试（延迟预算 +2s）。
- **涉及模块**：`agent/loop.py`、`tools/book_qa.py`。
- **工作量**：2 天。
- **验收**：false_refusal 下降 ≥ 30%，P95 仍 ≤ 8s。

### P2-4 流式协议细化

- **现状**：SSE 事件 intent/plan/tool/retrieval/context/delta/citations/done。
- **方案**：增加 `usage`（token/成本实时）、`tool_progress`（长工具心跳）、
  `suggestion`（追问推荐）；前端渲染"追问气泡"。
- **涉及模块**：`server/routes_public.py`、`web/app.js`。
- **工作量**：1 天。

### P2-5 多端：音箱语音流 + 电纸书离线

- **现状**：仅 Web；计划列了 5 端。
- **方案**：
  1. 音箱端：`/api/chat/voice`（ASR 文本入 → TTS 句级出），复用 SSE，句切分推送；
  2. 电纸书：阅读页内容包（章节 JSON）加 ETag/离线缓存清单接口，端侧缓存问答历史；
  3. 小程序：复用 OpenAPI，仅鉴权与合规审核（输出过 youth_mode）需关注。
- **涉及模块**：`server/`、`web/`。
- **工作量**：每端 2–4 天。
- **验收**：音箱链路首句出声 ≤ 2s；电纸书断网可读已缓存章节。

## 4. P3 · 推荐与离线算法升级

### P3-1 曝光去重与探索利用

- **现状**：推荐不去重近期已曝光书目；策略纯贪心打分。
- **问题**：首页反复同批书，用户体验差且长尾永远没机会（计划 §7 冷启动/长尾风险）。
- **方案**：
  1. 硬去重：7 天内已曝光 ≥ 3 次的书降权/过滤（读 events 即可）；
  2. 探索位：top_k 中 1 位按 ε-greedy（ε=0.1）从长尾池抽样（`rec.longtail_enabled` 已有雏形）；
  3. 进阶：Thompson Sampling 按 (clicks, impressions) Beta 分布采样热门分。
- **涉及模块**：`recommend/rules.py`、`recommend/rank.py`。
- **工作量**：2 天。
- **验收**：7 天窗口内首屏重复率 ≤ 20%；长尾书曝光占比 ≥ 10%。

### P3-2 多样性升级：MMR / 类目滑动窗口

- **现状**：类目硬上限（每类 ≤ 2）。
- **方案**：相似度感知的 MMR（用书目内容向量）：`λ·relevance − (1−λ)·max_sim`，
  避免同质书扎堆（如两本三国类）。
- **涉及模块**：`recommend/rules.py`、`rag/retriever.py`（复用向量）。
- **工作量**：1 天。
- **验收**： intra-list diversity 提升，NDCG 损失 ≤ 3%。

### P3-3 LTR 效果提升（AUC 0.5 → 0.70+）

- **现状**：逻辑回归 + 6 特征，演示埋点 4327 条，AUC 0.5（链路验证性质）。
- **方案**：
  1. 特征扩充：文本相关度特征（query-book 向量相似度）、深度行为（阅读时长/收藏）、
     交叉统计（用户-类目 CTR）、上下文（时段/端型）；
  2. 样本扩充：真实流量积累 + 负采样校准；样本表落库（point-in-time 快照）；
  3. 模型升级：XGBoost/LightGBM（排序），ONNX 导出在线打分；
  4. 训练/推理一致性校验脚本（同一特征函数复用，已有基础）。
- **涉及模块**：`offline/train.py`、`recommend/rank.py`。
- **工作量**：1–2 周（依赖真实流量）。
- **验收**：留出集 AUC ≥ 0.70；在线 A/B CTR +3%（Phase 2 目标）。

### P3-4 实时特征（session 内信号）

- **现状**：特征为 T-1 离线口径 + 消费侧增量，推荐不感知"本次会话刚看了什么"。
- **方案**：会话内实时特征通道：本次 session 的 click/read 即时写入
  `memory_short`（TTL 30min），推荐召回读取——"刚看完西游记 → 立刻推同类/同作者"。
- **涉及模块**：`events/collector.py`、`recommend/recall.py`、`conversation/session.py`。
- **工作量**：2 天。
- **验收**：会话内点击后下一次推荐首屏同类占比 ≥ 50%（新行为用例验证）。

### P3-5 离线调度与数据治理

- **现状**：特征重算/训练/候选集预计算为手动 CLI 或后台按钮；`purge_old_events` 有函数无调度。
- **方案**：
  1. 内置轻量调度器（APScheduler 或系统 cron 示例）：每小时特征增量、每日全量+训练+候选集、
     每周事件归档；
  2. 数据质量校验任务：事件量突降/特征空值/索引与库不一致告警；
  3. 特征点时快照表（训练样本快照，防特征穿越）。
- **涉及模块**：`offline/`、`ops/`、部署脚本。
- **工作量**：2–3 天。
- **验收**：断档一天后系统自愈；训练样本可复现（快照版本对齐）。

## 5. P4 · 工程与生产化

### P4-1 存储升级：SQLite → PostgreSQL/MySQL

- **现状**：SQLite WAL + 进程内写锁；单文件。
- **问题**：写并发上限低；无网络访问；备份/HA 需自建。
- **方案**：`db.py` 已是仓储层唯一 SQL 入口——迁移即换驱动 + 方言检查
  （`INSERT ... ON CONFLICT` 兼容 PG；`bm25()` FTS5 需换 ES/PG tsvector，见 P4-2）。
  建议顺序：先分域拆库（books/users/orders 各自独立），再换引擎。
- **工作量**：1–2 周。
- **验收**：全量测试 + 评测门禁在新存储上全绿。

### P4-2 检索引擎升级：FTS5 → Elasticsearch/OpenSearch

- **现状**：SQLite FTS5（jieba 预分词 + bm25）。
- **方案**：`db.fts_search` 与索引写入接口化（已有单点），实现 ES backend；
  同步获得 kNN 向量检索（替代内存暴力余弦）。数据 < 千万级前收益有限，
  触发条件：chunks > 50 万 或 QPS 检索延迟 > 100ms。
- **工作量**：3–5 天。

### P4-3 多实例部署清单（进程内状态外置）⚠️ 关键清单

| 进程内状态 | 位置 | 多实例后果 | 外置方案 |
|---|---|---|---|
| 事件消费线程 | events/collector | 重复消费 | P0-2；或独立 consumer 进程 |
| 限流器 | security/antifraud | 限额 ×N 失真 | Redis 滑窗/令牌桶 |
| 结果/语义缓存 | generation/answer | 命中率下降 | Redis（可 tolerate） |
| 指标 counters | obs/metrics | 各实例独立 | /metrics 多实例聚合（Prometheus 抓多目标即可，无需改） |
| 向量索引缓存 | rag/retriever | 各实例自加载（可接受） | 保持，重建信号走 DB 版本号 |
| A/B 分桶 | DB 持久化 | ✅ 已安全 | — |
| 会话/短期记忆 | DB | ✅ 已安全 | — |

- **验收**：2 实例压测下限流准确、事件零重复、缓存命中正常。

### P4-4 容器化与 CI/CD

- **方案**：Dockerfile（python:3.12-slim + requirements）+ docker-compose（app + PG + Redis +
  ES 可选）；CI：lint(ruff) → pytest → run_eval(离线) → 镜像构建；CD：灰度（先 1 实例
  摘流量跑门禁再全量）。健康检查用 `/api/health`。
- **工作量**：2–3 天。

### P4-5 可观测升级

- **现状**：JSON 日志 + trace_id + /api/metrics 文本。
- **方案**：
  1. OpenTelemetry SDK：trace 贯穿 网关→Agent→工具→模型网关（span 现成，接 exporter 即可）；
  2. 指标持久化：Prometheus + Grafana 大盘（聊天延迟/引用率/拒答率/工具成功率/成本）；
  3. 告警规则：P95 > 8s、拒答率 > 40%、LLM 错误率 > 5%、日成本 > 预算 80%。
- **工作量**：2–3 天。

### P4-6 压测与容量基线

- **方案**：Locust 场景（70% 问答 / 20% 推荐 / 10% 搜索），输出基线报告：
  单实例 QPS、P50/P95/P99、LLM 并发水位、慢查询清单；据此定 HPA 阈值与 LLM 限流参数。
- **验收**：产出 `docs/benchmark.md` 基线；问答 P95 ≤ 8s @ 目标并发。
